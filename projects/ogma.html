Ogma - Personal Spotify Wrapped

Inspired by the Celtic god of eloquence and learning, Ogma is a simple github repository activated by GitHub Actions that generates a Spotify Wrapped-like summary of my listening habits (weekly and monthly)

Status
In Progress
Start Date
June 2026
Tools
Python, GitHub, GitHub Actions, Spotify API, Last.fm API
  • web-development
  • music

Context

After the yearly Spotify Wrapped dropped, I became curious to get more data and on a more regular basis. The yearly wrapped is fun and you can see your new discoveries of the year but the data you get is only the one they want to show you, and you can't get it more than once a year. I wanted to have a more complete and regular overview of my listening habits, so I created Ogma. The name comes from the Celtic (Ogma for the Irish and Scottish and Ogmios for the Gallic people) god of eloquence and learning, who is said to have created the Ogham alphabet. I find the the name strikingly fitting as Ogma is a tool allowing me to inscribed and save my listening habits.

Realization

First version

Ogma V1 relied on the use of the Spotify API with which, it is quite easy to get data, however, there is no streaming history per se. You cannot simply ask for your last month or more of listening history, what you can get are the last 50 tracks played, nothing more. I had to go around and build the history myself, using a GitHub Action running everyday to get the last 50 tracks played and add them to a .json file inside the repository. This is a first real limitation, as if I listen to more than 50 tracks a day, I will lose informations on the tracks listened to earlier in the day. It can be estimated that the time required to listen to 50 tracks oscillates between 2h40 and 3h30, depending on the genre of music. To be sure to not lose any data, it is possible to simply run the GitHub Action more often, but the number of times I would listen to more than 50 tracks a day is not that high and running so many useless GitHub Actions would be a waste of resources.


For each track, it also recovers the name, artist, album and genre, to get a more complete overview. Then once per week a second GitHub Action is triggered to generate the weekly summary with the top 10 tracks, top 5 artists and genre and top 3 albums, as well as purging the previous history.json. But before purging, the history.json is pushed to the repository of website, so that I can display the summaries here in listening room.

In order to keep the important values that are the API keys from Spotify and GitHub to push the data to the other repo, they are placed inside secrets in the repository. It was fun to learn about the API calls and GitHub Actions, how to manage them and how to use them to recover data.

Second Version

In the middle of the redaction of this project page, I realised that I already used to track a bit my listening habits through Last.fm because it was linked to my Spotify. Stronger and wiser with my new knowledge of API's and the understanding that many websites and tools I used had their own API and often if not always free to use, I digged inside it. What a surprise, it already does what I tried to tinker with my small repo and actions.


The calls user.getTopTracks, user.getTopAlbums, user.getTopArtists and user.getTopTags can return the informations for up to 50 elements and from a specified time window. It is a moving window, so 1 week takes the data from the 7 previous days and month for the last 30 days. I decided to leave it this way, a day would not modify that much the results. It should also be noted that the their is already a weekly chart that can be extracted from Last.fm with one call, but I wanted to keep it my way.

Because these tools made my life much easier, I migrated to the new calls to recover data, as they would not require a daily call that could even miss songs in case of prolongated listening sessions. However, these calls have a small defect, they do not recover the pictures for the artists or the tracks, well they give you placeholders. Lucky for me I already set up the Spotify API, which can recover these images. By hybridizing the API calls I can recover the images for the top tracks and artists found using the user.getTop(..) from last.fm. It resulted in a much simpler file tree and fewer GitHub Action calls, only one per week and one per month (total 5 per month) versus one everyday + the weekly + the monthly (around 36 per month). The API calls are also much more reduced, instead of asking for all the previous listened to tracks, artists, album and genre from these tracks, it comes directly by 4 different calls. I just have to add the layer to Spotify, but it is focused on a small list.
